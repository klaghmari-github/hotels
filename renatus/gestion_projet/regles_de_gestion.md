# renatus

- Les contraintes suivantes doivent être obligatoirement respectée durant toute la vie du projet sans avoir besoin de les rappeler à chaque fois, ce sont les invariantes règles du projet :
- 100 % POO
- doc documenté de façon humaine, pas de caractères spéciaux, pas de commentaire bizarre. commentaire précis et concis et explicatifs.
- code bien optimisé bien refactorisé chaque classe joue bien son role, fonctionalités claires. lazy connection et lazy loading autant que possible via des properties.
- programmation TDD. toujours un agent entrain de coder la feature et un agent entrain de coder le test de la feature. le test doit être complet minimal et ciblant une feature. ca peut etre générer une base générer une table tester le resultat d'une requete et s'assurer du bon résultat tel que prévu.
- en cas de modification mineure on fait que des tests unitaires des nouvelles fonctionalités, en cas de modification majeure il faut rejouer tous les tests unitaires pour s'assurer que ca fonctionne comme prévue et que le développement de la nouvelle feature n'a pas cassé quelque chose.
- en cas d'anomalie détectée il faut l'inscrire dans la liste des anomalies fichers csv anomalies.csv et la traiter.
- les nouvelles features à réaliser seront inscrites dans le fichier features.csv. le statut crée ou created indique qu'elle vient juste d'etre crée et qu'elle attend qu'elle passe a prise en charge (en cours) et puis quand c'est fini elle passera à terminée.
- dans le projet il y a un agent watchdog qui suit  toute modification dans le dossier gestion_projet, s'il detecte une nouvelle feature il l'affecte à un agent disponible ou bien il attend qu'un agent se libère pour lui affecter la tâche. pendant que un agent developpe la feature le gestionnaire affecte la tâche de développer les tests de la features à un autre agent. donc une feature implique minimum 3 agent, un gestionaire, un developpeur et un testeur.
- pour l'anomalie, en général on a besoin que de deux agent, le gestionnaire et celui qui développe le correctif, pas besoin de developper le test car il existe déjà c'est l'echec du test qui est à l'origine de la création de l'anomalie.
- les features arrivent dans l'ordre et se partage le même contexte, c'est à dire qu'un élément mentionné dans la feature F001 peut être référencé dans la features F004.
- si le gestionnaire detecte qu'un statut d'une feature est annulée il notifie vite les agents pour arrêter de travailler dessus.
- le watchdog ne fait que écouter betement les modifications sur le dossier gestion_projet puis notifie l'agent gestionnaire de ces changement ce qui lui permet de prendre des décisions et de distribuer les tâches.
- certaines features peuvent s'exécuter en parallèle d'autres non.
- il faut développer en respectant une architecture git fastforward only. l'idée est que pour chaque feature demandée créer une branche à partir du main au meme nom de la feature, puis developper dessus, quand tout est bon faire le merge sur la branche develop.puis si ca passe faire le merge entre develop et main.
- il faut s'assurer d'avoir un lock au moment du merge request pour develop et pour main pour eviter deux merge request parallèle.
- si un MR echoue il faut analyser les ecarts et proposer la meilleure solution. et l'implementer pour corriger ça, en général un "rebase" suffit.
- si une feature est critique car on peut pas développer autre chose avant d'avancer dessus alors on essaye de mettre un maximum d'agents sur cette feature pour la finir au plus vite.
- les tests unitaires doivent idéalement être réalisés sur des bases de  données ou des fichiers de tests. eventuellement extrait des vraies bases ou des vraies fichiers mais en quantités beaucoup plus petites pour permettre un test rapide.
- dans la zone commentaire les agents developpeur ou testeurs peuvent ecrire des choses si necessaire ou si une decision importante a été prise car il n y avait pas de précision particulière et il fallait prendre une decision pour avancer sur le dev.
- l'agent développeur et l'agent testeur peuvent s'échanger des infos avec l'agent gestionnaire aussi et des devs peuvent être refais si ca echoue mais chaque agent dev ou test doit inscrire le temps passé qu'il a consommé dans sa tache de reflexion tout echange compris.  c'est à faire dans le fichiers anomalies.csv et features.csv.
- le cycle de dev est toujours branche crée du main, modification, merge avec develop, merge avec main, suppression de la branche feature. quand on fait un git push il faut marqué dans le commentaire la feature correspondante et décrire rapidement ce qu'on est entrain de faire, pour la meme features on peut faire plusieurs push avec des commentaires différents à chaque fois.
- quand on démarre la gestion du projet, le watchdog crée un fichier .running, rien que ma présence de ce fichier indique que le watchdog fonctionne. il doit rester fonctionnel même après traitement des features car on peut en ajouter.
- toute demande envoyée via la console grok doit être automatiquement convertie en feature et inscrite dans le fichier des features ou des anomalies. les idées s'incrémente F0001 F0002 F0003 etc et les anomalies aussi A0001 A0002 A0003 etc.
- le gestionnaire gere les fichier anomalies.csv features.csv et s'assure toujours que lui et ses agents respectent les règles du regles _de_gestion.md. ce fichier peut être modifié en life donc le watchdog notifie toute modification dans le dossier regles_de_gestion.
- une feature avec un statut vide est simplement une featture créé il faut la traiter aussi. quand on détecte un changemenhat on patiente 5seoncdes. et on check si pas de modification on considère que les modifications sont fini et que la feature est créee completement et donc on peut la lire et commencer son dev, si toutes les 5 secondes la features changes un peu on considère qu'elle est encours de création on patiente un peu.
- si je te pose une question je m'attend à juste une réponse dans le fichier questions_reponses_.csv dans le dossier de gestion, c'est pas forcément une feautre. tu me épond directement en console et tu sauvegarde ta réponse dans le fichier csv aussi .
- pendant la phase de dev/test il faut faire des push réguliers sur git sur la branche de la feature ou de l'anomalie afin que si l'ordinateur plante ou redemarre ou tombe en panne on perd pas les dev et on les garde en securité sur git pour reprendre plus tard.
- quand je te fais une remarque sur une gestion qui ne s'est pas bien passé tu l'ajoute en tant que règle pour ne pas refaire la meme betise une autre fois.
- en cas de conflits les règles ajoutées à la fin ecrasent les règles ecrites au début. en cas de conflit tu crée une feature dedié au conflit de règle mais c'est pas à toi de la gérer c'est moi qui va résoudre le conflit en t'indiquant quelle régle conserver finalement, mais par defaut la nouveauté ecrase l'ancienneté.
- les fichiers de coordination et notes des agents (notes_dev_Fxxxx.md, notes_test_Fxxxx.md, etat_agents.md, session.md, plan_Fxxxx.md, etat.json) se placent dans gestion_projet/agentic/ — c'est leur place naturelle. a la racine gestion_projet/ restent features.csv, anomalies.csv, regles_de_gestion.md, watchdog, locks, questions_reponses_.csv.
- separation stricte produit / gestion : le package src/renatus/ ne contient que du code metier (pipeline, cli, api, gui). tout code Python de gestion des agents vit sous gestion_projet/src/ (package agentic). donnees agents sous gestion_projet/agentic/. logs de gestion sous gestion_projet/logs/. ne jamais importer de modules de gestion depuis le package renatus ni y ajouter de sous-package agentic.
- le package et le depot renatus ne contiennent rien de specifique au projet hotels d origine (pas de data/ versionne, pas de sim_v1/sim_v2/ml, pas de models catboost/ml1). data/ et models/ sont runtime consommateur (gitignore). ne pas creer d arborescences vides metier dans le depot. Paths reste generique.
- les captures d ecran qui documentent bugs, anomalies ou features manquantes sont sauvegardees dans gestion_projet/agentic/captures/ et referencees dans la description de la feature ou de l anomalie (chemin relatif) pour tracabilite.
- tout long texte descriptif de feature, situation, avis technique ou spec envoye en console est sauvegarde dans gestion_projet/agentic/specs/ (fichier Fxxxx_*.md ou Axxxx_*.md) et reference dans features.csv ou anomalies.csv.
- features UI/GUI: tout element interactif important doit avoir un data-testid stable pour les tests E2E. les tests graphiques combinent unit (modele/API), E2E navigateur (Playwright) et eventuellement snapshots. le testeur s aligne sur des criteres d acceptation (AC) definis avec la feature, pas apres coup.
- qualite tests (F0028): apres une serie de features, faire un full check pytest. si une feature change de design et ecrase un contrat precedent, mettre a jour les tests ou les archiver sous tests/archive/ (pas de nom test_*.py dans archive pour eviter la collecte). les tests actifs sous tests/ doivent refleter uniquement l etat a jour du projet.

- Features majeures (refactor multi-modules, OOP large) se decomposent en sous-stories. Id parent: F00xx. Sous-stories: F00xx-S0, F00xx-S1, ... Chaque sous-story a sa ligne dans features.csv, un plan plan_F00xx-Sn.md si besoin, notes_dev/test, et peut recevoir un trio gestionnaire/dev/testeur comme une feature.
- Branche git: epic F00xx depuis main; story F00xx-Sn depuis F00xx (ou main si fichiers vraiment disjoints). Merge fast-forward only: story -> F00xx puis F00xx -> develop -> main. Locks develop/main restent obligatoires; pas de deux merge paralleles sur develop/main.
- Le parent F00xx ne passe a terminee que si toutes les sous-stories F00xx-S* sont terminees et qu un full pytest (modification majeure) est vert. Stories sur fichiers disjoints (ex. Python vs front) peuvent etre developpees en parallele avec des agents separes; stories qui touchent les memes fichiers restent sequentielles.
- Refactor majeur: pendant le developpement les tests unitaires de regression globaux peuvent etre mis en pause si le monolithe est en cours de decoupage; on privilegie des tests cibles par story. Des que le code est re-lie, on adapte les tests (chemins modules, helpers) puis on relance le full suite. Ne pas juger l epic sur une suite rouge pendant le demi-refactor.
- GUI front: privilegier data-testid, API et comportement. Les asserts qui lisaient uniquement src/renatus/gui/static/app.js passent par un helper de sources statiques (concat entry + modules) des que le JS est decoupe (F0028: mettre a jour ou archiver les contrats obsoletes).
- Agents paralleles sur une meme feature: le gestionnaire split en stories, assigne chaque story a un agent (ou pair dev/test), recoit les merges sur la branche epic, arbitre les conflits. Utiliser worktrees git isoles par story quand possible.
