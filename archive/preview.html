1. Objet et statut de la spécification

Ce document définit le comportement attendu du moteur de simulation. Il doit permettre à deux développeurs différents d’obtenir le même résultat à partir des mêmes données et du même scénario.

Ce document fixe

Les formules, l’ordre des traitements, les invariants, les fallbacks et les erreurs bloquantes.

Ce document distingue

Les règles mathématiques non configurables, les politiques de simulation configurables et les paramètres métier à valider.

Ce document n’inclut pas

Le nettoyage historique du fichier de marge. La source opérationnelle est déjà enrichie et fiable.

Statut cible. Cette v3 est la source de vérité durable du moteur. Elle ne dépend pas des étapes temporaires de dataprep.

2. Périmètre absolu : hôtel × solution

Les comportements d’achat diffèrent selon le dispositif de vente. Il est interdit de mélanger Simply, Liberty et Connected dans un même calcul de référence.

Simply

Produits exposés simplement ; paiement auprès d’un opérateur humain.

Liberty

Commande et paiement via borne.

Connected

Frigo connecté ou parcours self-service automatisé.

simulation_scope = HOTEL_CODE × SOLUTION
CalculAutoriséInterdit
Ranking localMême hôtel, même solutionAutre solution
Candidat multi-hôtelsAutres hôtels de la même solutionHôtel d’une autre solution
Médiane gammeMême solutionMédiane toutes solutions
Intensité panierFallback dans la même solutionFallback inter-solution
Coefficient de prixMême hôtel et même solution, puis même solutionCoefficient global non segmenté
Erreur bloquante. Toute fonction de simulation doit recevoir explicitement hotel_code et solution. Si la solution manque, le scénario est refusé.

3. Source d’entrée du moteur

Le moteur utilise une table ou un fichier de ventes étendu, déjà nettoyé et enrichi.

hotel_sales_raw_extended_data.xlsx
ou table de production équivalente

Cette source contient directement :

  • l’hôtel et la solution ;
  • le produit, la gamme et le type ;
  • les quantités vendues ;
  • le prix TTC unitaire ;
  • le prix marché fiable ;
  • la marge ligne ou les champs permettant de la recalculer ;
  • les identifiants panier / commande lorsque disponibles.
Règle documentaire. Le simulateur ne connaît jamais marges.xlsx, le scraping, les doublons de prix ni les étapes de consolidation. Ces sujets appartiennent à un document séparé et temporaire.

4. Concepts et définitions

Exposition pilote

Faute de table d’assortiment physique, le pilote infère qu’un produit était exposé lorsqu’il possède au moins une vente valide.

is_exposed_pilot = (STATUT = DONE) et (QUANTITE > 0)

Exposition scénario

Dans un scénario, l’exposition est décidée explicitement par le plan, indépendamment de la demande attendue.

is_exposed_scenario = décision du plan d’assortiment

Demande attendue

Les ventes simulées sont des espérances, éventuellement décimales. Une demande de 0,4 ne signifie pas 0,4 transaction réelle.

Produit atomique

Toute opération gamme ou type est transformée en opérations produit avant exécution.

Mix d’exposition

mix = nombre de produits exposés du segment / nombre total de produits exposés

Ce n’est ni un mix de ventes, ni de montant, ni de marge.

Plan atomique

Tous les retraits et ajouts sont résolus avant calcul. Le résultat ne dépend pas de l’ordre des actions utilisateur.

Distinction structurante. Dans le pilote, « exposé » est inféré depuis les ventes. Dans un scénario, « exposé » vient du plan et « ventes attendues » vient du modèle de demande.

5. Règles fixes, politiques configurables et paramètres métier

Règles fixes

  • Isolation hôtel × solution
  • Produit atomique
  • Plan atomique
  • Shares non renormalisés
  • Perte = D × SR
  • Paniers non additifs
  • Ratios toujours recalculés

Politiques configurables

  • demand_policy
  • basket_policy
  • mix_scope
  • capacity_mode
  • overflow_policy
  • seasonality_adjustment

Paramètres métier

  • plafond éventuel des nouveautés
  • minimum de mois observés
  • minimum de produits source
  • seuils de confiance
  • proxy de gamme

Aucune valeur métier, par exemple 40 %, ne doit être codée comme vérité mathématique. Elle doit être nommée, documentée et validée.

Une simulation d’assortiment ne change pas automatiquement le prix ni la marge unitaire. Un scénario de pricing serait un module distinct.

8. Ranking et qualité des candidats

8.1 Ranking de retrait

ORDER BY
  produit_marge_ventes_par_mois ASC,
  produit_nombre_ventes_par_mois ASC,
  produit_nombre_paniers_par_mois ASC,
  nombre_mois_observes DESC,
  produit_key ASC

Le dernier critère rend le tri déterministe.

8.2 Ranking d’ajout

ORDER BY
  marge_mensuelle_attendue DESC,
  ventes_mensuelles_attendues DESC,
  paniers_mensuels_attendus DESC,
  nombre_hotels_support DESC,
  produit_key ASC

Pour les familles à marge nulle ou proche de zéro, la rotation devient naturellement le premier critère discriminant.

8.3 Exclusion des artefacts

Les lignes invalides ou suspectes ne sont pas classées comme « mauvais produits ». Elles sont exclues et signalées.

QUANTITE > 0
PRIX_TTC > 0
PRIX_TTC_MARCHE >= 0
PRIX_TTC_MARCHE <= PRIX_TTC
clé produit complète
périmètre hôtel × solution valide

8.4 Éligibilité multi-hôtels

Un hôtel source ne contribue que s’il respecte :

same_solution = true
months_observed >= minimum_months
active_products_in_gamme >= minimum_products
median_gamme_sales > 0

Les seuils sont configurables et la confiance est stockée dans le résultat.

9. Suppression d’un produit

Entrée

remove_product(
  hotel_code="H001",
  solution="CONNECTED",
  product_key="P4"
)

Calcul

Q = Σ q_i
s_i = q_i / Q
D = q_r
S_R = s_r
q_i' = q_i + D × s_i, pour les produits restants
perte = D × S_R

Les shares utilisés sont ceux du snapshot avant plan. Ils ne sont pas renormalisés.

ProduitAvantShareAprès retrait de P4
P12020 %24
P24040 %48
P32020 %24
P42020 %retiré
Total100100 %96
Formule interdite. Renormaliser les shares des restants redistribuerait 100 % de la demande et ferait disparaître la perte comportementale.

10. Retraits multiples et plan atomique

Pour un ensemble de produits retirés R :

D = Σr∈R q_r
S_R = Σr∈R s_r
q_i' = q_i + D × s_i
perte = D × S_R

Exemple

Avec 20 / 40 / 20 / 20, retrait simultané de P3 et P4 :

D = 40 ; S_R = 0,40 ; perte = 16
P1' = 20 + 40 × 0,20 = 28
P2' = 40 + 40 × 0,40 = 56

Total final : 84.

Pourquoi atomique ? Retirer P3 puis recalculer avant P4 produirait un autre résultat. Le plan doit être résolu en bloc.

11. Ajout d’un produit

11.1 Hiérarchie des candidats

  1. Produit local retiré précédemment dans le même hôtel et la même solution.
  2. Produit réel présent dans d’autres hôtels de la même solution.
  3. Produit synthétique de même solution et même gamme.
  4. Proxy explicite de même solution pour une gamme inconnue.
  5. Sinon refus.

11.2 Rotation relative

rotation_relative(c,h) = ventes_mensuelles(c,h) / médiane_ventes_mensuelles(gamme,h)
rotation_relative(c) = médiane des hôtels admissibles de la même solution
ventes_attendues(c,cible) = rotation_relative(c) × médiane_ventes_mensuelles(gamme,cible)

11.3 Prix et marge attendus

coefficient_prix(cible,g) = médiane(prix_vente / prix_marché) dans la même solution
prix_vente_attendu = prix_marché_candidat × coefficient_prix
marge_unitaire_attendue = prix_vente_attendu − prix_marché_candidat
marge_mensuelle_attendue = ventes_mensuelles_attendues × marge_unitaire_attendue

11.4 Statut d’exposition

Le produit ajouté reçoit :

is_exposed = true
value_status = SIMULATED_EXPECTATION

Même si sa demande attendue est inférieure à une vente sur la période, il reste exposé et reçoit un warning. Il n’est pas supprimé automatiquement.

12. Demande, cannibalisation et débordement

12.1 Ordre contractuel

Retraits→ Perte des fans→ Demande brute nouveaux→ Cannibalisation→ Part additive

12.2 CONSTANT_MARKET

Le total après perte reste constant.

Q_remove = Σ q_i après retrait
A = Σ a_j, demande brute des nouveautés

Limite mathématique obligatoire :

A_max_math = Q_remove

Plafond métier facultatif :

A_max_business = cap × Q_remove, seulement si cap renseigné
A_max = min(A_max_math, A_max_business) si cap existe ; sinon A_max = Q_remove
scale = min(1, A_max / A)
a_j* = a_j × scale
q_i_final = q_i_remove × (1 − A* / Q_remove)
q_j_final = a_j*
Décision v3. Aucun plafond de 40 % n’est imposé par défaut. Un plafond métier éventuel est explicite, facultatif et validé par Accor.

12.3 ADDITIVE_MARKET

q_i_final = q_i_remove
q_j_final = a_j
Q_final = Q_remove + A

12.4 HYBRID_MARKET

λ ∈ [0,1]
C = (1 − λ) × A
E = λ × A
q_i_final = q_i_remove × (1 − C / Q_remove)
q_j_final = a_j
Q_final = Q_remove + E

13. Paniers et politique d’intensité stable

Les paniers ne sont pas additifs. La V1 estime les paniers en conservant l’intensité observée à chaque niveau.

intensité_hôtel = nombre_ventes / nombre_paniers
nombre_paniers' = nombre_ventes' / intensité_hôtel

Produit, gamme et type

paniers_niveau' = min(paniers_hôtel', ventes_niveau' / intensité_niveau)

Le plafond est appliqué individuellement, pas à la somme.

Situation normale. Σ paniers produit peut dépasser les paniers hôtel, car un même panier contient plusieurs produits.

Intensité d’un nouveau produit

  1. Médiane du même produit dans d’autres hôtels de la même solution.
  2. Sinon médiane des produits de la même gamme dans l’hôtel cible.
  3. Sinon médiane de la gamme dans d’autres hôtels de la même solution.
  4. Sinon intensité globale de l’hôtel cible.

Traçabilité

basket_estimation_method = STABLE_INTENSITY
basket_estimation_status = ESTIMATED
basket_intensity_source =
  PRODUCT_MULTI_HOTEL
  HOTEL_GAMME_MEDIAN
  SOLUTION_GAMME_MEDIAN
  HOTEL_FALLBACK

Les paniers simulés peuvent être décimaux et ne sont arrondis qu’à l’affichage.

14. Suppression d’une gamme

Une suppression de gamme est transformée en suppression de tous ses produits exposés dans le périmètre hôtel × solution.

Commanderemove_gamme("G2")
→
Plan résoluremove_product(P21...P60)

La demande totale retirée est calculée une seule fois, puis redistribuée une seule fois. Les agrégats gamme et type sont reconstruits après exécution.

15. Ajout d’une gamme

Gamme connue dans la même solution

Le moteur sélectionne les meilleurs candidats réels observés dans d’autres hôtels de la même solution.

Gamme inconnue dans l’hôtel mais connue ailleurs

Les profils sont réestimés dans l’hôtel cible à partir de rotations relatives, de prix et d’intensités de la même solution.

Gamme inconnue dans toute la solution

Deux choix seulement :

  1. fournir un proxy explicite dans la même solution ;
  2. refuser le scénario.
Interdit. Construire une gamme Connected à partir d’observations Simply ou Liberty.

16. Suppression d’un type

Supprimer un type signifie retirer toutes ses gammes et tous ses produits exposés dans le périmètre ciblé.

remove_type("NON-F&B")
→ resolve all exposed products
→ one atomic removal set
→ one loss calculation
→ one complete rebuild

17. Ajout d’un type

Ajouter un type nécessite de définir ou d’inférer ses gammes, leur répartition et leurs produits, toujours dans la même solution.

Répartition intra-type

Par défaut, si le type existe déjà :

part_gamme_dans_type = gamme_nombre_produits / type_nombre_produits

Pour un type totalement nouveau, la répartition doit être fournie ou provenir d’un proxy explicite de même solution.

18. Modification du mix d’exposition par gamme

mix_gamme(g) = nombre_produits_exposés(g) / nombre_total_produits_exposés

scope = specified — défaut

Les gammes non citées restent inchangées. Les pourcentages s’appliquent uniquement aux gammes citées.

scope = all

Toutes les gammes actives doivent être citées et la somme doit être égale à 100 %.

Capacité constante

N_final = N_initial

Capacité libre

target_n est obligatoire. Les pourcentages seuls ne suffisent pas.

Arrondis

Les effectifs cibles sont obtenus par la méthode des plus grands restes afin que leur somme soit exacte.

Exemple

G1 = 40, G2 = 60, cible 70/30, capacité 100 :

G1 : 70 → +30 produits
G2 : 30 → −30 produits

Les 30 retraits et 30 ajouts sont ensuite résolus au niveau produit.

19. Modification du mix d’exposition par type

mix_type(t) = nombre_produits_exposés(t) / nombre_total_produits_exposés

La cible type est transformée en effectifs, puis répartie entre les gammes du type.

Politique par défaut

intra_type_policy = PRESERVE_CURRENT_EXPOSURE

Exemple : F&B contient G1=30 et G2=20. Pour +10 produits F&B, l’allocation initiale est +6 G1 et +4 G2.

Une politique MAXIMIZE_EXPECTED_MARGIN peut être demandée explicitement, jamais activée silencieusement.

20. Reconstruction complète des indicateurs

20.1 Produit

produit_montant_ventes' = produit_nombre_ventes' × prix_unitaire
produit_marge_ventes' = produit_nombre_ventes' × marge_unitaire
produit_nombre_paniers' = min(paniers_hôtel', ventes' / intensité)

20.2 Gamme et type

ventes = Σ ventes produit
montant = Σ montant produit
marge = Σ marge produit

Les paniers sont estimés indépendamment avec l’intensité propre du niveau.

20.3 Hôtel

nombre_ventes = Σ produit_nombre_ventes
montant_ventes = Σ produit_montant_ventes
marge_ventes = Σ produit_marge_ventes

20.4 Ratios

Tous les champs suivants sont recalculés, jamais modifiés par delta :

_par_vente
_par_panier
_par_mois
mix_exposition
nombre_produits
nombre_gammes
nombre_types

22. Limites déclarées de la V1

22.1 Saisonnalité

seasonality_adjustment = NONE

La V1 utilise des moyennes mensuelles sans correction saisonnière. Un warning est produit si les périodes source et cible sont peu comparables.

22.2 Disponibilité et ruptures

availability_adjustment = NONE

Les ventes observées sont assimilées à la demande réalisée faute de données fiables sur les jours de disponibilité.

22.3 Paniers

Les paniers sont estimés, pas reconstruits transaction par transaction. Le statut doit rester ESTIMATED.

22.4 Faible historique

Les rankings bruts sont plus instables lorsque le nombre de mois ou de produits de référence est faible. La confiance doit être affichée.

24. Invariants et tests obligatoires

24.1 Invariants additifs

  • nombre_ventes = Σ produit_nombre_ventes
  • montant_ventes = Σ produit_montant_ventes
  • marge_ventes = Σ produit_marge_ventes
  • mêmes identités aux niveaux gamme et type

24.2 Invariants paniers

  • chaque panier produit/gamme/type ≤ paniers hôtel ;
  • les sommes de paniers par produit/gamme/type peuvent dépasser les paniers hôtel ;
  • aucune réconciliation additive n’est imposée.
