ml — chaîne de prédiction par solution

Documentation des étapes du moteur ml : dataset enrichi, modèle de taux de conversion, pont avec le simulateur de règles (sim_v2), puis modèle de chiffre d’affaires. Sans détail d’algorithme d’apprentissage — seul le rôle métier de chaque brique compte.

0 Objectif du moteur ml

sim_v2 estime déjà un CA à partir de règles (guests × m_lin × mix × coefficients). Le moteur ml complète cette vision en apprenant, sur les hôtels pilotes (observations + scénarios simulés), une correction qui tient compte du contexte de l’hôtel (proximité, météo, marque, structure, etc.).

Principe. On ne prédit pas le CA « en une seule boîte noire » à partir des seuls leviers. On enchaîne :
  1. apprendre le taux de conversion (ventes / guests) ;
  2. recaler le CA sim_v2 avec ce taux ;
  3. apprendre le CA final à partir du contexte + ce pont.
La décision métier du moteur « ml » est la sortie de l’étape 3 (CA final), par solution.
Pourquoi trois étapes ? Un ML qui ne prédit que le taux de conversion puis scale sim_v2 échoue souvent : le TC prédit n’est pas forcément le TC « compatible » qui redonnerait le bon CA. L’étape CA apprend la correction résiduelle entre le pont sim_v2×TC et la réalité.

Vue d’ensemble de la chaîne

┌─────────────────────┐ │ Dataset riche │ pivot sim_v2 (obs+sim) + contexte hôtel │ (par solution) │ + CA sim_v2 « brut » recalculé └──────────┬──────────┘ │ ▼ ┌─────────────────────┐ │ Étape A · ml_tc │ ML → taux de conversion │ │ features = leviers + mix + contexte + sim_v2_brut └──────────┬──────────┘ │ ▼ ┌─────────────────────┐ │ Étape B · pont │ (pas un modèle) │ ml_tc_sim_v2 │ CA_sim_v2 × (TC_prédit / TC_baseline_solution) └──────────┬──────────┘ │ ▼ ┌─────────────────────┐ │ Étape C · ml_ca │ ML → CA mensuel final │ │ features = celles de A + colonnes du pont B └──────────┬──────────┘ │ ▼ CA / solution → ROI / reco (modules communs)

Un couple de modèles (ml_tc + ml_ca) est entraîné par solution (simply / liberty / connected). Les fichiers sont stockés sous models/super/{solution}/.

1 Construction du dataset d’apprentissage

Traitement. On part du même nuage que sim_v2 : chaque ligne = un hôtel × scénario (observation ou simulation de retrait de natures). On joint le contexte hôtel et on recalcule le taux de conversion ligne à ligne.

taux_conversion = nombre_ventes_par_mois / nombre_guests_par_mois // recalculé pour obs ET sim (un scénario allégé a souvent un TC différent) // Exclusions dataset ML (ex.) hotel_code ∉ { H5586, H6188 }

2 Features autorisées (et fuites interdites)

Traitement. On construit un vecteur de variables numériques par ligne, sans jamais donner au modèle les cibles qu’il doit prédire.

// Inclus (descriptif + ancrage) CONTEXT : chambres, TO, guests/ch, m_lin MIX : parts type / gamme sim_v2_brut__* : CA et marges restitution sim_v2 pure px_*, wx_*, hd_*, hol_*, br_* : contexte // Interdit (fuites) montant_ventes_par_mois // cible CA montant_marge_* // cibles marge nombre_ventes_par_mois // fuite du TC taux_conversion // cible ml_tc scenario_id, hotel_code // identifiants
ml_ca réutilise les features de ml_tc et y ajoute uniquement les sorties du pont ml_tc_sim_v2__* (étape 4) — pas le CA réel.

3 Étape A — ml_tc (taux de conversion)

Traitement. Pour chaque solution, un modèle ML apprend à prédire le taux de conversion à partir des features descriptives + sim_v2_brut.

// Cible y = taux_conversion ∈ [0, 1] // Sortie TC_prédit = clamp( modèle_ml_tc(features) , 0, 1 )
ml_tc Rôle métier — « À quel rythme les clients hébergés achètent-ils ? » en tenant compte du contexte (pas seulement du profil pilote Excel).
Exemple conceptuel Simply.
TC baseline solution (moyenne obs) ≈ 0,034 · TC prédit pour une cible « centre-ville dense » pourrait monter à 0,045 → le pont (étape 4) gonflera le CA sim_v2 d’un facteur 0,045/0,034 ≈ 1,32.

4 Étape B — pont ml_tc_sim_v2 (sans modèle)

Traitement. On ne réentraîne rien : on applique le TC prédit sur le CA déjà fourni par la restitution sim_v2.

// Baseline = TC moyen observé de la solution (scénarios vides) TC_baseline(solution) // Pont ml_tc_sim_v2 = sim_v2_brut × ( TC_prédit / TC_baseline ) // Lecture « CA qu’aurait donné sim_v2 si on forçait le TC de ml_tc »
pont Rôle métier — garder l’ancrage des règles sim_v2 tout en injectant l’information de conversion apprise par le ML.
Exemple numérique.
sim_v2_brut = 800 € · TC_prédit = 0,040 · TC_baseline = 0,032
ml_tc_sim_v2 = 800 × (0,040 / 0,032) = 1 000 €

Même scaling pour les marges si présentes dans les colonnes sim_v2_brut.

5 Étape C — ml_ca (CA final)

Traitement. Un second modèle ML, toujours par solution, prédit le montant des ventes mensuel. Il voit le contexte + le pont de l’étape B.

// Cible y = montant_ventes_par_mois // Features = features de ml_tc ∪ { ml_tc_sim_v2__* } // Sortie (moteur ml) CA_ml = max( 0, modèle_ml_ca(features) )
ml_ca Rôle métier — correction résiduelle : le modèle apprend à coller au CA réel quand le pont seul ne suffit pas (effets marque, météo, proximité, non-linéarités, etc.).
Exemple. Pont = 1 000 € · CA réel d’un pilote similaire = 1 150 €.
ml_ca peut sortir ≈ 1 120 € en combinant le pont et les features de contexte.

6 Prédiction pour un hôtel cible (runtime)

Traitement. Même enchaînement qu’à l’entraînement, pour chaque solution :

  1. Assembler les leviers cibles + mix + features contexte (si hôtel connu) ;
  2. Calculer sim_v2_brut (restitution pure, même formule que sim_v2) ;
  3. ml_tc → TC_prédit ;
  4. pont → ml_tc_sim_v2 ;
  5. ml_ca → CA final (sortie moteur ml) ;
  6. Enrichissement ROI / reco (modules communs, hors ML).
// Pseudo-code runtime (par solution) features₀ = leviers + mix + contexte sim_v2_brut = restitution(features₀) TC = ml_tc(features₀ + sim_v2_brut) pont = sim_v2_brut × (TC / TC_baseline) CA = ml_ca(features₀ + sim_v2_brut + pont)
Les entrées utilisateur exploitables par ml sont celles de sim_v2 (chambres, TO, guests, m_lin, mix type/gammes) + éventuellement le code hôtel pour charger le contexte (proximité, météo, marque…).

7 Évaluations LOO et full

ModeTrainTestUsage
LOO Tous les hôtels de la solution sauf le cas exclu (si n ≥ 2) Hôtel exclu (obs) Mesure de généralisation « vrai » leave-one-out
full Tous les pilotes (obs + sim selon config) Même base (in-sample) Potentiel du modèle sans exclusion
Si une solution n’a qu’un seul hôtel pilote, le LOO ne peut pas exclure ce cas sans vider le train : l’évaluation est alors biaisée (signalé côté admin).

Exports : data/files/output/ml/eval_*_loo.xlsx, comparaison multi-moteurs dans l’admin.
