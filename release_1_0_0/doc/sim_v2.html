Vue d’ensemble — phases jusqu’au CA

Phase A — Construction (offline / pipeline) — source ventes → rangs → catalogue de scénarios → simulation par scénario × hôtel → t_dataset_pivot → coefficients par solution.
Phase B — Adaptation (online / prédiction) — lire leviers + mix de la cible → appliquer les coefficients de la bonne solution → agréger → CA mensuel par solution.

Les sections 1→6 décrivent la phase A (dataset par dataset). La section 7 et le lab appliquent la phase B sur vos entrées éditables.

1 Source & observation hôtel (dataset tickets)

Traitement. Les tickets pilotes (hotel_sales_raw_extended_data → t_sales) sont filtrés (prix/marge > 0). Pour chaque hôtel on agrège la période d’observation :

nombre_mois = DATE_DIFF(month, MIN(DATE), MAX(DATE)) + 1 nombre_guests_par_mois = chambres × TO × guests/ch × 30.5 nombre_ventes = Σ QUANTITE montant_ventes_par_mois = Σ PRIX_TTC / nombre_mois taux_conversion = nombre_ventes / nombre_guests (sur la période)
Exemple réel — H2075 Simply (Ibis budget Nice)
129 ch · TO 0,72 · guests 1,7 · m_lin 6 · 55 natures
guests/mois ≈ 4 816 · ventes/mois ≈ 164 · CA/mois ≈ 570 €
taux conversion ≈ 164 / 4 816 ≈ 3,4 %
Exemple — H0373 Connected (Mercure Montmartre)
305 ch · TO 0,76 · guests 2,0 · m_lin 6 · 56 natures
guests/mois ≈ 14 140 · CA/mois ≈ 3 432 €

2 Référentiels & rangs (dataset rank)

Traitement. On ordonne les NATURE_PRODUIT par performance dans chaque groupe (type, gamme, catégorie, marque, fournisseur) → tables t_rank_nature_by_*. Ces rangs guident quels ensembles de natures retirer pour générer des scénarios réalistes (on retire d’abord les natures les moins « centrales », ou on explore des retraits équilibrés par groupe).

Exemple. Pour un groupe « gamme SOS », les natures sont classées 1…N. Un scénario cumulatif peut retirer les k natures les moins bien classées, ce qui simule un assortiment SOS plus compact sans inventer de prix.

Code : ScenarioGenerator.generate_rank_scenarios · YAML 2_rank_pipeline.yaml.

3 Scénarios par hôtel (catalogue)

Traitement. Un scénario = ensemble (éventuellement vide) de natures à retirer. Le scénario vide = observation pure. Les autres = configurations d’assortiment plus resserrées. Stockage : t_scenarios / scenarios.xlsx (scenario_id, JSON des natures retirées).

scénario_vide → { } // observation scénario_ex → { "SANDWICH" } // 1 nature retirée scénario_ex2 → { "CACAHUETES", "SOUPE", … }
Exemple base release. ≈ 1 780 scénarios dans t_scenarios. Avec 6 hôtels pilotes → jusqu’à ≈ 10 680 lignes dans t_dataset_pivot (chaque couple scénario × hôtel).
À ce stade on n’a encore pas de CA cible : on prépare l’espace de configurations qui servira à apprendre les intensités.

4 Simulation scénario × hôtel (redistribution)

Traitement (4_simulation_pipeline.yaml) pour un scénario donné :

  1. Identifier tickets des natures retirées → volume retiré.
  2. Filtrer les tickets des natures conservées.
  3. Redistribuer le volume retiré sur les natures restantes (substitution proportionnelle aux parts historiques × taux de conversion).
  4. Scaler CA / marges linéairement avec les quantités.
  5. Ré-agréger mix (parts type/gamme en nombre de natures) et m_lin ajusté.
// Parts natures observées nature_part(h,n) = Σ Q(h,n) / Σ Q(h) // Volume retiré hôtel Q_retirees(h) = Σ Q sur natures du scénario // Réinjection sur nature conservée n Q_ajoutees(h,n) = Q_retirees(h) × taux_conversion(h) × nature_part(h,n) // Ligne ticket quantite_scenario = Q_ligne + Q_ajoutees × (Q_ligne / Q_nature) PRIX_TTC_scenario = PRIX_TTC × quantite_scenario / Q_ligne // Surface dataset m_lin_scénario = (m_lin_obs / n_natures_obs) × n_natures_après_scénario
Exemple H2075 Simply — retrait d’1 nature
OBS 55 natures · m_lin 6,00 · CA/mois 570,27 €
SIM 54 natures · m_lin ≈ 5,89 (= 6 × 54/55) · CA/mois typ. 559–569 € selon nature retirée
→ le CA bouge peu si la nature est marginale ; le mix (parts natures) se recentre.
Hypothèse métier : les clients des natures retirées se reportent sur le reste de l’assortiment. Ce n’est pas un modèle de cannibalisation fine produit à produit.

6 Coefficients d’intensité (adaptation par solution)

Traitement. On déplie le pivot en format long (une ligne par variable de mix), puis on calcule un coefficient unitaire :

// Pour chaque (scénario, hôtel, variable_mix) avec part > 0 montant_ventes_coefficient = montant_ventes_par_mois / (nombre_guests_par_mois × metres_lineaires × variable_part) // Puis moyenne par solution (obs + sim) coeff(solution, famille, variable) = AVG(montant_ventes_coefficient) GROUP BY solution, variable_family, variable_name

Lecture. CA mensuel par guest, par mètre linéaire, et par « point » de part de mix de cette variable. La bonne solution (simply / liberty / connected) sélectionne le bon groupe de coefficients à la prédiction.

Exemple coefficients TYPE (base release, moyenne sur obs+sim)
Solutiontype F&Btype NON F&B#obs
simply0,05440,0375~1 778
liberty0,03030,0215~3 500
connected0,11320,2099~5 300
Connected a des intensités F&B nettement plus élevées : volume / ticket moyen des pilotes Connected.
Vérification obs H2075 Simply sur type F&B
CA 570,27 / (4 815,83 × 6 × 0,4182) ≈ 0,047
(proche de la moyenne simply F&B 0,054 qui mêle aussi les scénarios simulés)

YAML : 5_restitution_base_pipeline.yaml → v_restitution_solution_coefficients.

7 Estimation CA hôtel cible (restitution)

Traitement. Pour chaque solution, chaque variable de mix avec target_part > 0 :

// Phase B — adaptation guests_c = chambres × TO × guests/ch × 30.5 CA_var(solution, variable) = coeff_ventes(solution, variable) × guests_c × m_lin_c × target_part(variable) // Agrégation publique sim_v2 (méthode moyenne des familles) CA_famille = AVG(CA_var) sur variables de la famille (type | gamme) CA_solution = AVG(CA_famille) sur les 2 familles
Exemple numérique — cible 100 ch · TO 70 % · 1,7 g · 4 m_lin · mix type 70/30
guests = 100 × 0,70 × 1,7 × 30,5 = 3 629,5
Simply · type F&B : 0,0544 × 3 629,5 × 4 × 0,70 ≈ 553 €
Simply · type N-F&B : 0,0375 × 3 629,5 × 4 × 0,30 ≈ 163 €
Moyenne famille type ≈ 358 € (ensuite moyenne avec famille gamme → CA final).
Les 3 solutions sont toujours évaluées en parallèle. Le choix « recommandée » peut ensuite venir de l’arbre Excel (reco.html) ou du meilleur ROI (roi.html).

YAML : 6_restitution_prediction_pipeline.yaml · API : SimV2Service.predict(...).
