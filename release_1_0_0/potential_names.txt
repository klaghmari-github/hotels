# Noms potentiels — package / projet open (ou interne)
# Outil : pipelines SQL déclaratifs multi-connexions (DuckDB d'abord)
#         + matérialisation à la demande (équivalent p_table_view)
#         + UI graphique arborescente (exploration, sample, build, remontée des depends)
#
# Contexte produit
# ----------------
# Core (déjà dans ce projet Accor) :
#   - graphe de dépendances (requires)
#   - types table / view / dataframe / iteration / execute
#   - modes create_if_not_exists | create_or_replace | …
#   - process_with_requires + frontier
#   - p_table_view(name) : build à la demande + remontée auto
#   - YAML pipeline + ConnectionPipeline
#
# Nouveau :
#   - package découplé métier Accor
#   - backends SQL quelconques (DuckDB, Postgres, …)
#   - UI : arbre / DAG, click nœud → sample, build si absent
#
# Critères de nommage retenus
# ---------------------------
# 1. Dit le "quoi" sans coller à Accor / hôtels
# 2. Court, pip-installable (minuscules, tirets OK)
# 3. Espace mental : arbre / graphe / matérialisation lazy / SQL
# 4. Laisse de la place pour le duo core + UI (ex. foo + foo-ui)
# 5. Pas déjà un outil SQL très connu (éviter sqlflow, sqlglot, dbt, dagster, …)
# 6. Prononçable FR + EN
#
# Légende des scores (subjectifs) : ★★★★★ = meilleur fit produit


# =============================================================================
# A. SHORTLIST PRIORITAIRE (réflexion profonde → top recommandations)
# =============================================================================

1. demandql
   Score: ★★★★★
   Idée: "demand-driven SQL" — le cœur de p_table_view : on demande un nœud,
         le graphe se matérialise en remontant les depends.
   Core: demandql   UI: demandql-ui / demandql studio
   + très fidèle au modèle mental ; unique ; moderne
   − moins explicite sur "pipeline" pour un lecteur pressé

2. arborsql
   Score: ★★★★★
   Idée: arbre (arbor) de relations SQL — UI = arborescence native.
   Core: arborsql   UI: arborsql-ui / Arbor Studio
   + métaphore visuelle parfaite pour le click-on-node
   − "arbor" un peu savant ; vérifier dispo PyPI/npm

3. sqlloom
   Score: ★★★★☆
   Idée: on tisse (loom) des dépendances SQL en un tissu de tables/vues.
   Core: sqlloom   UI: sqlloom-studio
   + beau, mémorable, product-like
   − métaphore un cran plus abstraite que "tree/build"

4. sproutsql
   Score: ★★★★☆
   Idée: les tables "poussent" (sprout) à la demande quand on ouvre un nœud.
   Core: sproutsql / sprout-sql
   + excellent pour lazy create_if_not_exists + UX build-on-click
   − un peu "cute" pour un outil data enterprise (peut être un plus open-source)

5. frontierql
   Score: ★★★★☆
   Idée: reprend votre concept interne stable_frontier — la frontière de build.
   Core: frontierql / sqlfrontier
   + ancré dans l'algo déjà développé ; différenciant tech
   − moins intuitif hors de votre équipe

6. viewgraph
   Score: ★★★★☆
   Idée: graphe de vues/tables SQL explorables.
   Core: viewgraph   UI: viewgraph-ui
   + clair, direct
   − "view" masque un peu tables / iterations / executes

7. pullsql
   Score: ★★★★☆
   Idée: pull-based materialization (on tire un nœud → dépendances suivent).
   Core: pullsql
   + simple, technique exacte (vs push ETL)
   − peut évoquer CDC / replication "pull"

8. reltree
   Score: ★★★☆☆
   Idée: arbre de relations (tables/vues).
   Core: reltree
   + ultra-court, collé à l'UI arborescente
   − générique ; collision possible avec d'autres "rel*"

# I. STRUCTURE DE PRODUIT SUGGÉRÉE (quel que soit le nom N)
# =============================================================================
#
#   N                 # package core Python
#                     #   - PipelineSpec (YAML/dict)
#                     #   - DependencyTree / frontier
#                     #   - Connection backend protocol (DuckDB, SQLAlchemy, …)
#                     #   - materialize(name)  ≈ p_table_view

#   N-ui / N-studio   # app graphique
#                     #   - arbre / DAG
#                     #   - click → preview
#                     #   - bouton Build → materialize + refresh état
#   N-cli             # optionnel : N materialize v_hotel_clients
#
# Exemples d'API mentale (indépendants du nom) :
#
#   from demandql import Pipeline
#   p = Pipeline.from_yaml("pipeline/", conn=duckdb_conn)
#   p.materialize("v_hotel_clients")   # remontée auto des requires
#   p.sample("v_hotel_clients", n=20)
#   p.status("v_hotel_clients")        # missing | ready | stale
#
#   demandql-studio ./pipeline --db main.duckdb
