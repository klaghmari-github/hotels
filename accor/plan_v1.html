Plan de migration du simulateur v1 vers les pipelines YAML

Comparaison des strategies v1 et v2, faisabilite d une reimplementation du moteur Excel (R1 a R4) avec le gestionnaire de pipelines DuckDB, fichiers d entree a prevoir, architecture cible et points de vigilance.

1. Synthese executive

Conclusion : oui, le simulateur v1 peut etre migre vers une implementation par pipelines YAML et le pipeline manager de main.py. Ce n est pas un simple copier-coller des regles Python : il faut reecrire le moteur en SQL declaratif (ou hybrider SQL + etapes execute), charger les references Excel en tables, et redefinir le leave-one-out v1 dans le meme style que le pipeline 7 de la v2.

Source de verite v2 : docs/documentation_complete_simulation_restitution_loo.html (completee par README.md, main.py et config/). La v2 enchaine trois objectifs : modelisation (assortiment), restitution (coefficients par solution), evaluation LOO. La v1 reste un moteur reglementaire Excel (R1 a R4, marges, couts). Les deux LOO ne mesurent pas le meme objet.

Correction par rapport a une interpretation anterieure : la restitution v2 ne choisit pas "la simulation la plus proche en mix". Elle calcule des coefficients unitaires par variable de mix, puis reconstruit la cible. Les hotels de solutions differentes ne sont jamais melanges dans ces agregations.

2. Strategie v2 (selon la documentation complete)

2.1 Trois objectifs successifs

Donnees pilotes-> Scenarios de modelisation-> Coefficients de restitution-> Predictions par solution-> Evaluation LOO

2.2 Modelisation (pipelines 0 a 4)

  • Unite atomique : NATURE_PRODUIT (retrait de groupe = liste de natures).
  • Ventes = SUM(QUANTITE), jamais un comptage de lignes.
  • Filtre source : PRIX_TTC > 0 AND MARGE > 0.
  • Scenario = liste canonique de natures retirees + hash SHA-256, appliquee a tous les hotels.
  • Guests mensuels (caracteristique fixe de l hotel) : chambres x TO x guests/chambre x 30,5.
  • Metres lineaires variables selon le scenario : m_lin_par_nature = m_lin_observes / n_natures_observees, puis m_lin = m_lin_par_nature x n_natures_restantes (0 si plus aucune nature).
  • Redistribution : ventes_recuperees = ventes_retirees x taux_conversion, ajout_nature = ventes_recuperees x part_nature, sans renormalisation (part des natures retirees perdue).
  • Montants proportionnels a la quantite scenario pour PRIX_HT, PRIX_TTC, PRIX_TTC_MARCHE, MARGE_SELON_COEF, MARGE.
  • Mix d exposition = parts en nombre de natures distinctes (pas en volume). Dimensions : type, gamme, categorie, marque, fournisseur.
  • Dataset final t_dataset_pivot : une ligne par scenario_id x hotel_code, avec trois cibles mensuelles : ventes TTC, marge selon coef, marge marche.
  • Parallelisation : buckets de scenarios, workers DuckDB, frontiere stable, schema pivot exact, reprise sur scenario_id + hotel_code.

2.3 Restitution (pipelines 5 et 6)

Estimer les performances mensuelles d un hotel cible pour chaque solution (Simply, Liberty, Connected), sans rejouer les retraits de natures.

Entrees uniquement :

  • chambres, TO, guests/chambre (donc guests mensuels) ;
  • metres lineaires souhaites ;
  • parts de types et de gammes (predicteurs independants) ;
  • coefficients appris sur les simulations de modelisation.

Normalisation par variable de mix j :

coefficient_j = cible_mensuelle / (guests_mensuels x metres_lineaires x part_j)

Agrege par (solution, variable_family, variable_name). Puis : 

prediction_j = coefficient_moyen_j x guests_cible x m_lin_cibles x part_cible_j

Variables a part nulle exclues de la moyenne finale.

Methodes A et B

  • A : moyenne de toutes les predictions de variables (type + gamme). Donne plus de poids a la famille qui a le plus de variables.
  • B : moyenne des types, moyenne des gammes, puis moyenne des deux familles (poids equivalent type / gamme).

Sortie : deux lignes par solution (A et B) pour les trois cibles (CA, marge coef, marge marche). API : run_restitution(...).

2.4 Leave-One-Out (pipeline 7)

  1. Selectionner un hotel a evaluer.
  2. Exclure toutes ses simulations de l apprentissage.
  3. Conserver uniquement les hotels de la meme solution.
  4. Recalculer les coefficients moyens de restitution.
  5. Recuperer le contexte reel (guests, m_lin) et le mix observe de l hotel exclu (scenario initial : liste de natures retirees vide).
  6. Predire les trois cibles mensuelles avec A et B.
  7. Comparer aux valeurs observees du scenario initial.

Metriques : MAE, RMSE, MAPE, biais (global et par solution). La methode retenue pour la restitution finale est celle qui performe le mieux en LOO, en priorite sur la marge puis sur le CA. Iteration sequentielle (tasks: 1), sans buckets.

API : run_leave_one_out(cp, rebuild=True).

3. Strategie actuelle v1 (Excel ROD)

3.1 Modelisation

Le moteur v1 n est pas un moteur de retraits de natures. C est le simulateur Excel ROD (Simply / Liberty / Connected) :

  1. R1 - clients acheteurs (taux acheteur et panier de la reference).
  2. R2 - impact du mix F&B (+/- 10 %).
  3. R3 - coefficients categories produit (besoins clients).
  4. R4 - surface (m_lin) ou frigos (Connected).
  5. Marge produit - CA - CA/coef (coef F&B / N-F&B selon solution).
  6. Couts - techno, annexes, agencement (barèmes JSON / Excel).
  7. Marge nette et amortissement.

Reference = pivots solution (rod_reference.json, pilot_table.py) et/ou moyenne des hotels pilotes de la solution. Code principal historique : RevenueRules, CostRules, rod_excel_sim, applications admin/user.

3.2 Evaluation leave-one-out v1 (implementation actuelle)

  • run_eval_sim_v1.py + logique associee : pour chaque hotel pilote H, on exclut H, on reconstruit la reference avec les pairs de sa solution, on applique R1-R4 sur les parametres de H.
  • Metriques : MAE / MAPE sur CA et marge, detail par hotel.
  • Pas de catalogue de milliers de scenarios d assortiment : le "modele" est deterministe et le LOO porte sur la reference pilote.

3.3 Donnees d entree v1 typiques

Les deux LOO sont valides, mais ils ne mesurent pas la meme chose. Un MAE v1 et un MAE v2 ne sont pas directement comparables sans aligner la definition de la cible (CA mensuel baseline, meme hotels, meme periode).

5. Faisabilite d une v1 "pipeline YAML"

Oui, c est possible. Le pipeline manager de main.py n est pas reserve a l assortiment v2. Il sait : charger des Excel/JSON en dataframes, creer tables/vues SQL, iterer (sequentiel ou parallele), inserer de facon idempotente.

5.1 Ce qui se mappe bien en YAML + SQL

  • Chargement des sources (hotel_data, sales, rod_reference aplatis).
  • Construction des indicateurs hotel (clients/mois, mix F&B, m_lin).
  • Reference solution (moyenne des pilotes, avec exclusion LOO).
  • Chaine R1 a R4 et marge produit en SQL (formules arithmetiques + CASE pour Connected / frigos).
  • Table de resultats hotel x solution, metriques MAE / MAPE.
  • Iteration leave-one-out sur la liste des hotels (comme i_loo_evaluation).

5.2 Ce qui reste plus naturel en Python (hybride acceptable)

  • Parsing riche de rod_reference.json (cost_lines imbriquees) avant injection en tables plates.
  • Arbre de recommandation (seuils chambres, lifestyle N-F&B, TO) : expressible en SQL CASE, ou en etape execute / fonction Python.
  • UI Flask (run_eval_sim_v1) : hors pipeline, lit les tables resultats comme la v2 pourrait le faire.
Point important : "possible en pipeline" ne signifie pas "tout coller dans un seul SELECT". L architecture v2 montre le bon pattern : beaucoup de vues SQL + un peu de Python pour l orchestration et les entrees dynamiques (run_restitution, replace_step_view).

6. Plan de migration propose

Etape 0 - Perimetre fonctionnel

  • Phase A (prioritaire) : revenus R1-R4 + marge produit (+ alignement explicite marge coef vs marge marche si on veut la parite avec les trois cibles v2).
  • Phase B : couts + marge nette + amortissement + reco solution.
  • LOO v1 = exclusion de H dans la reference pilote / pivots, puis rejeu des regles Excel. Ce n est pas le LOO coefficients v2 (pas de decomposition guests x m_lin x part pour la v1 historique).
  • Pattern d orchestration a reutiliser de la doc v2 : sources -> tables stables -> vues de calcul -> iteration sequentielle -> table resultats -> metriques. Parallelisme inutile pour 7 hotels.

Etape 1 - Base et sources

  1. Creer une base dediee, par exemple duckdb/pilotes/sim_v1/sim_v1.duckdb (ne pas melanger avec sim_v2).
  2. Dossier de config separe, par exemple config_v1/ (ou prefixe v1_* dans un dossier dedie) pour ne pas polluer les pipelines v2.
  3. Reutiliser ConnectionPipeline de main.py (import partage) plutot que dupliquer le manager.

Etape 2 - Tables de reference

Charger et aplatir les JSON Excel en tables DuckDB (voir section entrees).

Etape 3 - Indicateurs hotel et reference solution

t_hotel_params
  hotel_code, solution, nb_chambres, to, guests, m_lin, mix_fb, clients_mois, ...

t_solution_reference          -- moyenne de tous les pilotes de la solution
t_solution_reference_loo      -- moyenne sans l hotel de v_loo_step

Etape 4 - Moteur R1-R4 en vues SQL

Chaque vue consomme la precedente. Les overrides de reference (LOO) passent par la vue step d iteration, comme en v2.

Etape 6 - UI

Adapter run_eval_sim_v1.py pour lire t_v1_loo_results / v_v1_loo_metrics (comme lecture Excel aujourd hui), sans recalculer en Python.

Etape 7 - Parite et bascule

  • Jeu de tests : meme hotels, memes entrees, comparer CA et marge pipeline vs RevenueRules.compute (ecart max par ex. 0,01 EUR).
  • Une fois la parite validee, marquer l ancien chemin Python comme legacy (admin/user peuvent encore l utiliser tant que la parite n est pas etendue aux couts).

Flux LOO v1 en pipeline

Formules SQL cibles (phase A)

clients_mois_h = nb_chambres * to * guests * 30.5
taux_acheteur  = nb_ventes_ref / clients_mois_ref
nb_acheteurs   = clients_mois_h * taux_acheteur
ca_fb_r1       = (ca_fb_ref / nb_ventes_ref) * nb_acheteurs
ca_nf_r1       = (ca_nf_ref / nb_ventes_ref) * nb_acheteurs

steps          = (mix_fb_h - mix_fb_ref) * 10
ca_fb_r2       = ca_fb_r1 + ca_10_fb * steps
ca_nf_r2       = ca_nf_r1 + ca_10_nfb * (-steps)

-- R3 : mult_fb / mult_nfb selon besoins (tous ON en eval, ou table de besoins)
ca_fb_r3       = ca_fb_r2 * mult_fb
ca_nf_r3       = ca_nf_r2 * mult_nfb

-- R4 Simply/Liberty
ca_fb_r4       = ca_fb_r3 + sign(m_lin_h - m_lin_ref) * ca_1ml_fb * abs(diff)
-- R4 Connected : frigos (CASE)

marge          = (ca_fb - ca_fb/coef_fb) + (ca_nf - ca_nf/coef_nf)

9. Points bloquants et non-bloquants

9.1 Non bloquants (a traiter, mais standards)

PointMitigation
JSON imbrique (couts, concepts) Pre-aplatissement vers Excel/CSV de reference
R3 multi-categories Table de coefficients + somme conditionnelle ; en eval, forcer tous les besoins a ON comme aujourd hui
R4 Connected (frigos) Branches SQL CASE sur solution
Parite numerique avec Python Tests de regression hotel par hotel vs RevenueRules.compute
UI existante Brancher la lecture sur DuckDB / Excel exporte depuis t_v1_loo_results

9.2 Points de vigilance (pas d impossibilite)

  • Regles proceduales longues : une seule vue monolithe sera illisible. Il faut un chainage de vues (comme v2), pas un unique SQL de 500 lignes.
  • Couts Excel : plus fragiles a porter en pur SQL (lignes conditionnelles, amortissements). D ou la phase B separee.
  • Paralleleisme : peu utile pour un LOO de 7 hotels. Garder execution: sequential sur l iteration v1.
  • Contamination v2 : ne pas reutiliser t_dataset_pivot v2 comme moteur v1. Bases et configs separees.
  • Definition de la marge reelle : aligner explicitement marge marche vs marge selon coef dans les metriques LOO v1, comme en restitution v2.

9.3 Ce qui bloquerait vraiment (et ce n est pas le cas ici)

Un blocage dur existerait si le moteur dependait d un apprentissage non expressible en SQL batch (modele ML opaque, optimisation iterative non tabulaire). Ce n est pas le cas de la v1 Excel : les regles sont algebraiques et finies. Donc pas de point bloquant structurel.

10. Criteres de reussite de la migration

  1. python -c "from main_v1 import run_v1_loo; ..." (ou equivalent) produit t_v1_loo_results sans appeler RevenueRules en boucle Python.
  2. Ecart absolu max CA et marge produit < 0,05 EUR vs implementation Python de reference sur les 7 hotels pilotes (hors cas limites documentes).
  3. Leave-one-out : un hotel exclu n apparait jamais dans sa propre reference solution.
  4. L interface d evaluation v1 lit les resultats pipeline (onglets data / eval_H / eval) sans recalcul.
  5. Documentation courte dans le README v1 : sources, formules, commande de rebuild.

11. Recommandation operationnelle

Faire

  • Migrer d abord revenus + LOO (phase A).
  • Partager le pipeline manager de main.py.
  • Isoler config et DuckDB v1.
  • Aplatir les JSON en tables.
  • Valider par parite numerique.

Ne pas faire

  • Melanger scenarios d assortiment v2 et regles Excel v1.
  • Forcer le LOO coefficients v2 sur la v1.
  • Reporter les couts avant d avoir la parite R1-R4.
  • Reecrire un second manager de pipelines parallele.

En resume : la migration v1 vers pipelines est realiste et souhaitable pour unifier l outillage avec la v2. Le travail principal est de translation des regles Excel en chaine de vues SQL + sources de reference bien modelisees, pas un obstacle conceptuel.
