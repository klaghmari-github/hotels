1. Objectif général

Le moteur construit des variantes simulées des hôtels pilotes en modifiant uniquement la configuration du corner. Les caractéristiques structurelles de l’hôtel restent fixes pendant cette phase : solution, capacité hôtelière, taux d’occupation, nombre de guests par chambre et période d’exposition.

Chaque scénario est défini uniquement par une liste de natures de produits à retirer. La même liste est appliquée à tous les hôtels. Si une nature existe dans un hôtel, elle est retirée. Si elle n’existe pas, le scénario n’a aucun effet sur cette nature pour cet hôtel.

→

→
Simulation par hôtel
→
Recalcul des indicateurs
→
Dataset hôtel × scénario

2. Principes structurants

Nature de produit

Unité atomique de suppression. Une nature peut regrouper plusieurs produits ou formats physiques.

Quantité vendue

Le nombre de ventes métier est toujours calculé avec SUM(QUANTITE). COUNT(*) n’est pas utilisé pour mesurer les ventes.

Exposition

La présence dans le corner est mesurée par des comptages distincts de natures, catégories, gammes, types, marques et fournisseurs.

Scénario commun

Une liste de natures est simulée simultanément sur tous les hôtels, sans dimension hotel_code dans l’identité du scénario.

Référence immuable

t_sales reste la baseline. Chaque simulation repart des données observées et ne dépend pas du scénario précédent.

Recalcul déclaratif

Les vues en create_or_replace sont recalculées à chaque scénario. Les tables persistantes sont conservées.

4. Fonctionnement du gestionnaire de pipeline

Le dossier de configuration peut contenir plusieurs fichiers YAML. Ils sont chargés récursivement et fusionnés dans un seul dictionnaire logique. Chaque objet est décrit par un type, un mode, ses dépendances et éventuellement une requête SQL.

TypeComportement
dataframeCharge un fichier en DataFrame puis l’enregistre dans DuckDB.
tableCrée une table physique à partir d’une requête.
viewCrée ou remplace une vue logique.
executeExécute une requête sans créer d’objet portant le nom du nœud.
iterationParcourt une table de scénarios, remplace une vue d’étape et lance une cible pour chaque ligne.

Modes de création

ModeDécisionTraitement des dépendances
create_if_not_existsL’objet est créé seulement s’il n’existe pas.Les dépendances ne sont traitées que si la création est nécessaire.
create_or_replaceL’objet est systématiquement recalculé.Les dépendances sont recalculées avant lui.

Cette logique évite de relire le fichier Excel à chaque scénario tout en garantissant que toutes les vues dépendant du scénario courant sont actualisées.

5. Construction des classements

Les tables de ranking ordonnent les natures et les groupes par marge croissante. Les éléments les moins intéressants économiquement sont donc placés en premier.

5.1 Classement global des natures

Pour chaque hôtel :

marge(nature) = Σ MARGE des lignes appartenant à la nature

Le rang est calculé avec :

ROW_NUMBER() OVER (
    PARTITION BY hotel_code
    ORDER BY montant_marge, nature
)

5.2 Classement des natures dans chaque groupe

Le même principe est appliqué à l’intérieur de chaque catégorie, gamme, type, marque et fournisseur.

5.3 Classement des groupes

La marge d’un groupe est la somme des marges de ses natures. La table de groupe contient également la liste des natures déjà ordonnée, ce qui permet de convertir directement la suppression d’un groupe en liste atomique de natures.

6. Génération des scénarios

La classe ScenarioGenerator construit plusieurs familles de scénarios :

  1. scénario vide : aucune nature retirée ;
  2. retraits cumulatifs des natures globales les moins rentables ;
  3. retraits cumulatifs des natures les moins rentables à l’intérieur de chaque groupe ;
  4. retraits cumulatifs des groupes les moins rentables ;
  5. scénarios de modification de mix ;
  6. scénarios de réduction des mètres linéaires.

6.1 Canonicalisation

Avant enregistrement, chaque liste est :

  • nettoyée des valeurs nulles et vides ;
  • dédupliquée ;
  • triée de façon stable et insensible à la casse pour l’ordre principal.

Ainsi, les listes suivantes représentent le même scénario :

["Coca", "Eau"]
["Eau", "Coca"]
["Coca", "Eau", "Coca"]

6.2 Scénarios cumulatifs

Si le ranking est N1, N2, N3, N4, les scénarios produits sont :

[]
[N1]
[N1, N2]
[N1, N2, N3]
[N1, N2, N3, N4]

La suppression complète est autorisée lorsque include_full_removal=True. Un hôtel peut donc obtenir zéro vente et zéro marge si toutes ses natures sont retirées.

7. Identifiant stable du scénario

L’identifiant n’est pas un numéro séquentiel. Il est calculé à partir de la liste canonique, sérialisée en JSON compact, puis passée dans SHA-256. 

canonical = ["Coca", "Eau"]
payload = '["Coca","Eau"]'
scenario_id = SHA256(payload)

Ce choix apporte quatre garanties :

  • une même liste possède toujours le même identifiant ;
  • l’ordre d’entrée n’a aucun impact ;
  • les doublons sont automatiquement neutralisés ;
  • les exécutions futures peuvent reconnaître un scénario déjà calculé.

8. Exécution itérative des scénarios

La table t_scenarios contient une ligne par liste canonique. L’étape i_iteration_scenario la parcourt dans l’ordre défini.

À chaque itération, une table temporaire d’une ligne est créée, puis exposée par v_scenario_step. Toutes les vues dépendantes sont ensuite recalculées.

8.1 Reprise automatique

L’itération peut déclarer une table de résultats déjà calculés. Les scénarios dont le hash existe déjà sont exclus de la liste à exécuter. 

WHERE NOT EXISTS (
    SELECT 1
    FROM t_dataset_pivot AS completed
    WHERE completed.scenario_id = scenarios.scenario_id
)

10. Calcul des guests et du taux de conversion

Le nombre moyen de guests mensuels est une propriété de l’hôtel :

Guests mensuels = Chambres × Taux d’occupation annuel × Guests par chambre × 30,5

Le nombre de mois d’exposition est :

Nombre de mois = DATE_DIFF('month', MIN(DATE), MAX(DATE)) + 1

Le nombre total de guests sur la période est :

Guests période = Guests mensuels × Nombre de mois

Le taux de conversion observé est :

Taux de conversion = Σ QUANTITE / Guests période
Ces valeurs restent fixes pour tous les scénarios de retrait ou de mix. Elles sont lues depuis t_sales, et non depuis la vue filtrée du scénario.

11. Redistribution des ventes après retrait

La suppression d’une nature retire d’abord ses ventes observées. Les acheteurs correspondants redeviennent des clients potentiels. Une partie seulement reconvertit, selon le taux de conversion de l’hôtel.

11.1 Volume potentiel récupéré

D = Ventes retirées × Taux de conversion

11.2 Modèle de préférence pilote

Pour chaque nature i :

Part pilote(i) = Ventes observées de i / Ventes observées totales

La quantité ajoutée à une nature restante est :

Ajout(i) = D × Part pilote(i)

Les parts ne sont pas renormalisées sur les seules natures restantes. La fraction de D correspondant aux natures supprimées est donc perdue.

11.3 Répartition dans les lignes historiques

Une nature peut être représentée par plusieurs lignes. L’ajout attribué à la nature est réparti entre ses lignes proportionnellement à leur quantité historique :

Part ligne = QUANTITE ligne / Ventes observées de la nature
QUANTITE scénario = QUANTITE ligne + Ajout(nature) × Part ligne

12. Recalcul des montants et des marges

Le prix unitaire implicite de chaque ligne est conservé. Les montants sont ajustés au prorata de la nouvelle quantité.

PRIX_TTC scénario = PRIX_TTC observé × QUANTITE scénario / QUANTITE observée
MARGE scénario = MARGE observée × QUANTITE scénario / QUANTITE observée

Le même mécanisme s’applique à :

  • PRIX_HT ;
  • PRIX_TTC ;
  • PRIX_TTC_MARCHE ;
  • MARGE.
Les lignes ayant une quantité observée nulle ne doivent pas être présentes dans le jeu de modélisation, car les formules utilisent NULLIF(QUANTITE, 0).

13. Reconstruction du mix d’exposition

Le mix est calculé à partir des natures encore présentes dans v_sales_current. Il ne dépend ni du nombre de lignes ni des quantités vendues.

13.1 Comptages globaux

  • nombre_natures = nombre distinct de NATURE_PRODUIT ;
  • nombre_categories = nombre distinct de catégories ;
  • nombre_gammes = nombre distinct de gammes ;
  • nombre_types = nombre distinct de types ;
  • nombre_marques = nombre distinct de marques ;
  • nombre_fournisseurs = nombre distinct de fournisseurs.

13.2 Colonnes dynamiques

Les noms sont normalisés puis pivotés, par exemple :

categorie_boissons_nombre_natures
gamme_snacking_nombre_natures
type_f_b_nombre_natures
marque_coca_cola_nombre_natures
fournisseur_x_nombre_natures

Le pourcentage associé est :

Part du groupe = Nombre de natures du groupe / Nombre total de natures

Les pivots dynamiques sont matérialisés en tables create_or_replace, car DuckDB n’autorise pas un pivot dynamique directement dans une vue.

14. Dataset pivot final

Le dataset final contient une ligne par couple scenario_id × hotel_code. Il réunit :

Identité

Hash du scénario, liste des natures retirées, code hôtel.

Contexte

Solution, mètres linéaires, nombre de mois, guests mensuels.

Cibles

Ventes mensuelles, montant des ventes mensuel, marge mensuelle.

Configuration

Effectifs et pourcentages du mix par catégorie, gamme, type, marque et fournisseur.

L’insertion est idempotente grâce à un contrôle sur scenario_id et hotel_code.

15. Fonction principale d’orchestration

La fonction main() exécute le processus complet :

  1. ouvre la base DuckDB ;
  2. charge et fusionne les pipelines YAML ;
  3. construit les scénarios à partir des rankings ;
  4. écrit data/scenarios.xlsx ;
  5. rafraîchit t_scenarios ;
  6. vérifie la compatibilité du schéma de t_dataset_pivot ;
  7. compte les résultats déjà présents ;
  8. lance l’itération uniquement sur les scénarios manquants ;
  9. retourne le dataset final et les statistiques d’exécution.

display(simulation["scenarios"])
display(simulation["result"])

16. Suivi de progression

Avant le lancement, les logs indiquent :

Scenarios total : 1250 | deja calcules : 800 | a simuler : 450

Puis, pour chaque scénario :

Scenario 37/450 | id=4e51... | debut
Scenario 37/450 | id=4e51... | duree=3.8s | ecoule=141.2s | reste_estime=1577.3s

L’estimation restante est calculée sur la durée moyenne observée depuis le début :

Temps restant estimé = Durée moyenne par scénario × Nombre de scénarios restants

17. Idempotence et reprise après interruption

Le moteur ne vide plus systématiquement la table finale. À chaque lancement :

  1. la liste complète des scénarios est régénérée ;
  2. les hashes sont recalculés de façon déterministe ;
  3. les scénarios dont le hash existe déjà dans la table cible sont ignorés ;
  4. seuls les scénarios absents sont simulés.
Une interruption du notebook ne fait pas perdre le travail déjà réalisé. Le prochain lancement reprend automatiquement sur les scénarios non calculés.

20. Exemple numérique complet

Supposons un hôtel avec :

  • 1 000 guests sur la période ;
  • 200 ventes observées ;
  • 20 ventes portées par les natures retirées ;
  • une part pilote totale de 10 % pour les natures retirées.

Étape 1 — taux de conversion

200 / 1 000 = 20 %

Étape 2 — ventes potentielles récupérées

20 × 20 % = 4 ventes potentielles

Étape 3 — application des préférences

Les parts pilotes sont appliquées sans renormalisation. Les natures restantes reçoivent 90 % de ces 4 ventes :

4 × 90 % = 3,6 ventes redistribuées

La part correspondant aux natures retirées est perdue :

4 × 10 % = 0,4 vente perdue

Étape 4 — total final

200 − 20 + 3,6 = 183,6 ventes

Les quantités, montants et marges des lignes restantes sont ensuite recalculés proportionnellement, puis agrégés et mensualisés.
