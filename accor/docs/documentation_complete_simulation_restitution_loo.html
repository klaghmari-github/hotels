1. Objectif general

Le projet poursuit trois objectifs successifs.

  1. Generer des hotels simules a partir des hotels pilotes en faisant varier leur assortiment.
  2. Construire un moteur de restitution capable d'estimer les performances mensuelles d'un hotel cible pour chaque solution.
  3. Evaluer objectivement les methodes de restitution avec une procedure Leave-One-Out.

2. Hypotheses principales

  • La nature de produit est l'unite atomique de retrait.
  • Un retrait de gamme, type, categorie, marque ou fournisseur est converti en liste de natures a retirer.
  • Le nombre de ventes correspond a la somme de QUANTITE, jamais au nombre de lignes.
  • Les hotels utilisant des solutions differentes ne sont jamais melanges dans les agregations de restitution.
  • Les caracteristiques fixes de l'hotel sont le nombre de chambres, le taux d'occupation annuel et le nombre de guests par chambre.
  • Les valeurs economiques sont mensualisees avant comparaison ou restitution.
  • Les parts de types et de gammes sont des variables descriptives independantes utilisees comme predicteurs.
  • Les lignes avec vente non positive ou marge non positive sont exclues des le chargement de t_sales.
Le moteur peut produire un scenario avec zero vente et zero marge pour un hotel si toutes ses natures sont retirees. Ce resultat est volontaire.

3. Preparation des donnees source

3.1 Filtre qualite

La table t_sales ne conserve que les lignes suivantes :

PRIX_TTC > 0
AND MARGE > 0

Ce filtre exclut les valeurs nulles, negatives et les ventes sans information economique exploitable.

4. Generation des simulations de modelisation

Les simulations de modelisation partent de la configuration observee de chaque hotel pilote. Chaque scenario contient une liste ordonnee et dedupliquee de natures a retirer. La meme liste est appliquee a tous les hotels.

4.1 Familles de scenarios

  • Retraits cumulatifs des natures les moins rentables au niveau global.
  • Retraits cumulatifs dans chaque categorie.
  • Retraits cumulatifs dans chaque gamme.
  • Retraits cumulatifs dans chaque type.
  • Retraits cumulatifs dans chaque marque.
  • Retraits cumulatifs dans chaque fournisseur.
  • Retraits cumulatifs de groupes entiers classes par marge.

4.2 Classement

Les natures et groupes sont classes par marge croissante. Les elements ayant le moins d'interet economique sont retires en premier.

marge_groupe = somme des marges des natures appartenant au groupe

5. Identite et generation des scenarios

5.1 Canonicalisation

Chaque liste de natures est nettoyee, dedupliquee et triee.

["Eau", "Coca", "Eau"]
devient
["Coca", "Eau"]

5.2 Hash stable

Le champ scenario_id est un SHA-256 calcule sur la representation JSON compacte de la liste canonique.

scenario_id = SHA256(JSON(liste_canonique))

Le hash permet de reconnaitre un scenario deja calcule, quel que soit l'ordre initial des natures.

6. Calcul d'un scenario de modelisation

6.1 Retrait des ventes observees

Les lignes correspondant aux natures retirees sont exclues de la vue courante. Le volume retire est :

ventes_retirees = somme de QUANTITE sur les natures retirees

6.2 Taux de conversion de l'hotel

taux_conversion = nombre_ventes_observees / nombre_guests_observes

6.3 Ventes potentielles recuperees

ventes_recuperees = ventes_retirees × taux_conversion

6.4 Redistribution selon le pilote

La part pilote de chaque nature est calculee sur les ventes observees de l'hotel :

part_nature = ventes_nature / ventes_totales_hotel

La quantite ajoutee a une nature restante est :

ajout_nature = ventes_recuperees × part_nature

Les parts ne sont pas renormalisees apres retrait. La part correspondant aux natures retirees est donc perdue.

6.5 Recalcul des montants

Les montants de chaque ligne restante evoluent proportionnellement a la nouvelle quantite.

valeur_scenario = valeur_observee × quantite_scenario / quantite_observee

Cette formule est appliquee a :

  • PRIX_HT
  • PRIX_TTC
  • PRIX_TTC_MARCHE
  • MARGE_SELON_COEF
  • MARGE

7. Mix d'exposition et metres lineaires

7.1 Mix d'exposition

Le mix est calcule a partir du nombre distinct de natures encore actives. Il ne depend pas des quantites vendues.

part_groupe = nombre_natures_du_groupe / nombre_natures_total

Les dimensions calculees sont :

  • type
  • gamme
  • categorie
  • marque
  • fournisseur

7.2 Metres lineaires par nature

Pour chaque hotel, le metre lineaire moyen d'une nature est calcule a partir de la configuration observee.

metres_lineaires_par_nature = metres_lineaires_observes / nombre_natures_observees

7.3 Metres lineaires du scenario

metres_lineaires_scenario = metres_lineaires_par_nature × nombre_natures_restantes

Le meme produit peut donc correspondre a une surface moyenne differente selon l'hotel.

8. Execution parallele des simulations

Les scenarios sont repartis dans des buckets independants. Chaque bucket utilise une base DuckDB worker distincte.

8.1 Repartition

bucket_id = entier_base_16(scenario_id) modulo nombre_de_buckets

8.2 Nombre de workers

Par defaut, le nombre de buckets et de workers est calcule avec deux processeurs logiques reserves au systeme.

workers = max(1, nombre_vCPU - 2)

8.3 Frontiere stable

Le graphe de dependances remonte depuis la cible d'iteration jusqu'aux objets en create_if_not_exists. Ces objets sont copies dans les workers. Le type logique est preserve : une table reste une table et une vue reste une vue.

8.4 Schema exact de la table resultat

La table t_dataset_pivot est recreee dans chaque worker a partir du schema DuckDB exact de la base partagee. Cette approche evite les erreurs d'inference de type provoquees par les DataFrames vides.

8.5 Reprise

Un scenario deja present dans la table finale n'est pas recalcule. Les resultats locaux des workers sont fusionnes dans la base partagee avec controle d'unicite sur : 

scenario_id
hotel_code

10. Generation des simulations de restitution

La restitution estime les performances mensuelles d'un hotel cible pour chaque solution. Elle utilise uniquement :

  • les trois champs permettant de calculer les guests mensuels ;
  • les metres lineaires souhaites ;
  • les parts des types ;
  • les parts des gammes ;
  • les trois cibles economiques mensualisees.

10.1 Input hotel

ChampSignification
hotel_nb_chambresNombre de chambres.
hotel_to_annuelTaux d'occupation annuel.
hotel_guests_per_chambreGuests moyens par chambre occupee.
metres_lineairesSurface lineaire cible du corner.

10.2 Input mix

Le mix est fourni au format long avec une ligne par variable : 

variable_family | variable_name              | target_part
type            | type_f_b_part_natures      | 0.70
type            | type_non_f_b_part_natures  | 0.30
gamme           | gamme_g1_part_natures      | 0.30
gamme           | gamme_g2_part_natures      | 0.20

11. Normalisation des simulations

Chaque colonne de part est traitee comme un predicteur independant de la cible totale. Pour une variable de mix j :

coefficient_j = cible_mensuelle / (guests_mensuels × metres_lineaires × part_j)

Le calcul est effectue separement pour :

  • montant_ventes_par_mois
  • montant_marge_selon_coef_par_mois
  • montant_marge_par_mois

Les coefficients sont ensuite agreges par :

solution
variable_family
variable_name
coefficient_moyen = moyenne des coefficients des hotels et scenarios de la meme solution

11.1 Prediction d'une variable

prediction_j = coefficient_moyen_j × guests_cible × metres_lineaires_cibles × part_cible_j

Une variable dont la part cible est nulle n'est pas utilisee dans la moyenne finale.

12. Methodes de restitution A et B

12.1 Methode A : moyenne globale

Toutes les predictions issues des variables de types et de gammes sont mises dans une seule moyenne.

prediction_A = moyenne de toutes les predictions de variables actives

Cette methode donne naturellement plus de poids a la famille contenant le plus de variables.

12.2 Methode B : moyenne equilibree par famille

La moyenne des types est calculee separement de la moyenne des gammes.

prediction_type = moyenne des predictions de types
prediction_gamme = moyenne des predictions de gammes
prediction_B = moyenne(prediction_type, prediction_gamme)

Cette methode attribue un poids equivalent aux familles type et gamme.

12.3 Sortie de restitution

13. Evaluation Leave-One-Out

Le Leave-One-Out evalue chaque hotel a tour de role.

  1. Selectionner un hotel a evaluer.
  2. Exclure toutes ses simulations de la base d'apprentissage.
  3. Conserver uniquement les hotels appartenant a la meme solution.
  4. Recalculer les coefficients moyens de restitution.
  5. Recuperer le contexte reel et le mix observe de l'hotel exclu.
  6. Predire ses trois cibles mensuelles avec les methodes A et B.
  7. Comparer les predictions aux valeurs observees du scenario initial.

13.1 Scenario observe de reference

La valeur reelle de l'hotel est issue de la ligne dont la liste de natures retirees est vide. 

LEN(scenario_removed_natures) = 0

13.2 Iteration

L'iteration LOO est sequentielle avec tasks: 1. Elle est rapide et ne necessite ni buckets, ni workers, ni reprise complexe.

14. Metriques d'evaluation

Les metriques sont calculees globalement et par solution.

MetriqueFormuleInterpretation
MAEMoyenne des erreurs absoluesErreur moyenne dans l'unite de la cible.
RMSERacine de la moyenne des erreurs au carrePenalise davantage les grandes erreurs.
MAPEMoyenne des erreurs relatives absoluesErreur moyenne en proportion de la valeur reelle.
BiaisMoyenne prediction moins observationDetecte une sur-estimation ou une sous-estimation systematique.

La comparaison finale porte sur les methodes A et B pour les trois cibles :

  • montant des ventes mensuel ;
  • marge mensuelle selon coefficient ;
  • marge mensuelle selon prix du marche.
La methode retenue pour la restitution finale sera celle qui obtient les meilleures performances Leave-One-Out, en priorite sur la marge puis sur le montant des ventes.
